# Tech Stack และเหตุผลที่เลือก

> อัปเดตล่าสุด: 2026-08-19

เอกสารนี้บันทึก **การตัดสินใจ** พร้อมเหตุผล ไม่ใช่แค่รายการเทคโนโลยี — เพื่อให้ตอนกลับมาอ่านทีหลังจะรู้ว่าทำไมถึงเลือกแบบนี้ และเงื่อนไขไหนที่ควรเปลี่ยนใจ

## สรุป

| ส่วน | เลือกใช้ | เวอร์ชันที่ติดตั้งจริง |
|---|---|---|
| Framework | Next.js (App Router) + TypeScript | 16.3.1 |
| UI | Tailwind CSS | v4 |
| Runtime | React | 19.2.8 |
| ฐานข้อมูล | PostgreSQL + PostGIS (ผ่าน Supabase) | — |
| Auth / Storage | Supabase | — |
| แผนที่ | Leaflet + OpenStreetMap | — |
| Hosting | Vercel (แอป) + Supabase (ข้อมูล) | — |

## การตัดสินใจที่สำคัญ

### 1. Next.js เดียว ไม่แยก Frontend / Backend เป็นคนละ service

**ทางเลือกที่พิจารณา:** แยก React (Vite) + Node/Express API เป็นคนละโปรเจกต์

**ที่เลือก:** Next.js ตัวเดียว โดยแยกเป็นชั้นภายใน repo เดียวกัน

```
src/app/          → หน้าเว็บ (UI)
src/app/api/      → HTTP endpoint (backend)
src/lib/          → business logic + data access
```

**เหตุผล:**

1. **SEO เป็นช่องทางโตหลักของโปรเจกต์นี้** เว็บรวมอีเวนต์อยู่ได้ด้วย organic search และการแชร์ลิงก์ผ่าน LINE/Facebook ถ้าเป็น SPA ล้วน หน้าเว็บจะไม่มีเนื้อหาตอนบอทมาเก็บข้อมูล และลิงก์ที่แชร์จะไม่ขึ้น preview — Next.js render ฝั่งเซิร์ฟเวอร์ให้ฟรี
2. **ลดงาน DevOps ของคนทำคนเดียว** deploy ที่เดียว ไม่ต้องตั้งค่า CORS ไม่ต้องดูแล 2 service
3. **ยังต่อยอดเป็นแอปมือถือได้** ถ้าวันหนึ่งทำ native app ก็ให้แอปยิงมาที่ `src/app/api/` ซึ่งเป็น JSON API อยู่แล้ว ไม่ต้องรื้อ

**เงื่อนไขที่ควรกลับมาทบทวน:** ถ้ามีทีม backend แยกจริงจัง หรือมี consumer หลายตัวที่ต้องใช้ API ชุดเดียวกันจนตรรกะเริ่มไม่เข้ากับ web app

### 2. PostgreSQL + PostGIS แทนที่จะเก็บ lat/lng เฉยๆ

ฟีเจอร์แกนของเว็บคือ **"งานใกล้ฉัน"** ซึ่งต้องเรียงตามระยะทางจริงบนผิวโลก ไม่ใช่ผลต่างของตัวเลขพิกัด PostGIS ให้ `ST_DWithin` และ `ST_Distance` ที่คำนวณเป็นเมตรถูกต้อง และมี GIST index ทำให้ query เร็วแม้ข้อมูลเยอะ

เขียนเองด้วยสูตร haversine ก็ได้ แต่จะ index ไม่ได้ — ต้องคำนวณทุกแถวทุกครั้ง ซึ่งพังเมื่อข้อมูลโตขึ้น

### 3. Supabase แทนการตั้ง Postgres เอง

ได้ Postgres + PostGIS + Auth + Storage + Row-Level Security ในที่เดียว มี free tier ใช้งานได้จริง และไม่ต้องดูแลเซิร์ฟเวอร์ ตรงกับข้อจำกัด "คนเดียว งบยังไม่มี"

ที่สำคัญคือ **ยังเป็น Postgres มาตรฐาน** ถ้าวันหนึ่งอยากย้ายไป Neon, RDS หรือเซิร์ฟเวอร์ตัวเอง ก็ย้าย schema ไปได้ ไม่ได้ล็อกตายกับ vendor

### 4. Leaflet + OpenStreetMap แทน Google Maps

Google Maps คิดเงินต่อการโหลดแผนที่ ซึ่งอันตรายกับเว็บที่ตั้งใจให้มีทราฟฟิกเยอะแต่ยังไม่มีรายได้ — บิลโตตามความสำเร็จ Leaflet + OSM ไม่มีค่าใช้จ่ายต่อ request

ส่วนการแปลงที่อยู่เป็นพิกัด (geocoding) เกิดเฉพาะตอนแอดมินกรอกงาน ซึ่งปริมาณน้อยมาก จะใช้บริการไหนก็ได้โดยไม่กระทบต้นทุน

### 5. ค้นหาด้วย `pg_trgm` ไม่ใช่ full-text search

Postgres full-text search **ตัดคำภาษาไทยไม่ได้** เพราะภาษาไทยไม่มีช่องว่างระหว่างคำ ตัว tokenizer มาตรฐานจะมองทั้งประโยคเป็นคำเดียว

`pg_trgm` ทำงานระดับตัวอักษร 3 ตัวติดกัน จึงค้นหาคำที่อยู่กลางข้อความภาษาไทยได้ เหมาะกว่าในบริบทนี้ ถ้าข้อมูลโตจนไม่พอค่อยพิจารณา Meilisearch หรือ Typesense ที่รองรับภาษาไทยโดยตรง

### 6. ธีม Dark เดียว ไม่สลับตาม `prefers-color-scheme`

เลือกให้เว็บใช้จานสีเข้มเป็นค่าเดียวเสมอ แทนที่จะสลับตามระบบปฏิบัติการของผู้ใช้ เหตุผล:

1. **เข้ากับธีมงานเทศกาลกลางคืน** โคมไฟ ไฟประดับ และแสงไฟงานวัด ดูมีมิติกว่าบนพื้นเข้ม
2. **ดูแลง่ายกว่าสำหรับคนทำคนเดียว** ไม่ต้องไล่ตรวจ contrast คู่สีทั้ง 2 ธีมทุกครั้งที่เพิ่ม component ใหม่

ถ้าอนาคตอยากได้ light mode ทางเลือก แนะนำทำเป็นสวิตช์ในหน้าตั้งค่าที่ผู้ใช้กดเลือกเอง
(เก็บค่าไว้ใน localStorage) แทนการอิงระบบปฏิบัติการอัตโนมัติ เพราะควบคุมและทดสอบง่ายกว่า

### 7. ตัวกรองค้นหาใช้ "soft navigation" ไม่ใช่ client-side filter เต็มรูปแบบ

หน้า `/events` ต้อง server-render ตาม `searchParams` เสมอเพื่อ SEO (ดูเหตุผลข้อ 1 ด้านบน)
แต่การรีเฟรชหน้าทั้งหน้าทุกครั้งที่เปลี่ยนตัวกรองให้ความรู้สึกช้า จึงแก้ด้วยการให้
`src/components/event-filters.tsx` เป็น Client Component ที่ดักการเปลี่ยนค่า แล้วเรียก
`router.push()` ของ Next.js แทนการ submit ฟอร์มแบบเบราว์เซอร์ปกติ

ผลคือ: URL ยังเปลี่ยนตามตัวกรองเหมือนเดิม (แชร์ลิงก์ได้ Google เก็บ index ได้เหมือนเดิม)
หน้า `/events/page.tsx` ยังเป็น Server Component อ่าน `searchParams` เหมือนเดิมทุกอย่าง
แต่ผู้ใช้ไม่เห็นจอขาววาบเวลาเปลี่ยนตัวกรอง

ฟอร์มยังเป็น `<form method="get" action="/events">` เป็นฐานไว้ก่อนเสมอ — ถ้า JavaScript
โหลดไม่สำเร็จ ฟอร์มยัง submit แบบเบราว์เซอร์ปกติได้ (progressive enhancement)

### 8. ภาพประกอบการ์ดงานเป็น SVG แทนภาพถ่ายจากเว็บภายนอก

ตอนนี้การ์ดงานใช้ภาพประกอบไล่สี (gradient/bokeh) ที่ generate ด้วย SVG ตามสี accent ของแต่ละหมวดหมู่
(`src/components/event-cover.tsx`) แทนการหยิบภาพถ่ายสต็อกจากเว็บภายนอกมาใช้ เพราะไม่มีทาง
ตรวจสอบล่วงหน้าว่าลิงก์ภาพจากเว็บอื่นจะยังใช้งานได้และตรงเนื้อหาในระยะยาว

เมื่อต่อ Supabase Storage แล้ว (Phase 1) ให้เปลี่ยนไปแสดง `event.coverImageUrl` จริงแทนที่นี่
ฟิลด์นี้มีอยู่แล้วในโครงสร้างข้อมูล ไม่ต้อง migrate เพิ่ม

### 9. แผนที่จังหวัดใช้ SVG ที่ generate เอง ไม่ใช่ Leaflet

หน้า `/map` ต้องการแค่ "รูปร่างจังหวัดที่กดได้ ระบายสีตามจำนวนงาน และซูมเข้าได้"
ไม่ต้องการภาพถ่ายดาวเทียมหรือถนน จึงใช้ inline SVG ซึ่งไม่ต้องเพิ่ม dependency,
คุมสีให้เข้าธีม Dark ได้เต็มที่ และ server-render ได้ (บอทกับผู้ใช้เน็ตช้าเห็นแผนที่ตั้งแต่ HTML แรก)

ต่างจาก `src/components/event-map.tsx` ที่ใช้ iframe จาก OpenStreetMap — อันนั้นทำหน้าที่
"ปักหมุดจุดเดียวให้กดไปนำทางต่อ" คนละงานกัน จึงคงไว้ตามเดิม

**ที่มาข้อมูลและลิขสิทธิ์:** `thailand-adm1-polygons-v1.0.0.geojson` จาก
[DevelopedbyWill/thailand-canonical-admin-names](https://github.com/DevelopedbyWill/thailand-canonical-admin-names)
ใบอนุญาต **CC BY 4.0** (ใช้เชิงพาณิชย์ได้ ต้องให้เครดิต) อ้างอิงข้อมูลกรมแผนที่ทหารผ่าน OCHA CODs

> ⚠️ **เครดิตใน `src/components/site-footer.tsx` ห้ามลบ** — เป็นเงื่อนไขบังคับของใบอนุญาต

เคยพิจารณา [BorntoDev/Thailand-Map-Vector](https://github.com/BorntoDev/Thailand-Map-Vector) แต่ไม่เลือกเพราะ
มีแต่ไฟล์ `.ai` กับ `.png` (ต้องไล่จับคู่ 77 รูปร่างกับจังหวัดด้วยมือ) และใช้ CC BY-**SA**
ซึ่งบังคับให้งานดัดแปลงต้องใช้ลิขสิทธิ์เดียวกัน — เป็นข้อผูกมัดที่ควรเลี่ยงสำหรับเว็บที่จะหารายได้

**การแปลงข้อมูล:** `npm run build:map` อ่าน GeoJSON → project ด้วย Web Mercator →
เขียน `src/lib/data/province-paths.ts` (96 KB → 22 KB) ทำตอน build ครั้งเดียว จึงไม่ต้องส่ง
ไลบรารี projection ไปให้เบราว์เซอร์ ไฟล์ผลลัพธ์ generate ใหม่ได้เสมอ **ห้ามแก้ด้วยมือ**

**อนิเมชั่นซูม:** ใส่ CSS `transform` ที่ `<g>` ที่ครอบ path ทั้ง 77 อัน ไม่ animate `viewBox`
เพราะเบราว์เซอร์ transition ค่านั้นให้ไม่สม่ำเสมอ ส่วน transform ทำงานบน GPU
และเคารพ `prefers-reduced-motion` โดยตัดการเคลื่อนไหวออกแต่ยังซูมไปตำแหน่งที่ถูกต้อง

## หมายเหตุสำหรับ Next.js 16

เวอร์ชันนี้มีจุดที่ต่างจากบทความ/ตัวอย่างเก่าๆ ที่หาเจอในเน็ต:

- `params` และ `searchParams` เป็น **Promise** ต้อง `await` ก่อนใช้
- มี type helper `PageProps<'/events/[slug]'>` และ `LayoutProps<'/'>` ให้ใช้แทนการประกาศ type เอง (generate ตอนรัน `next dev`)
- `fetch` **ไม่ cache อัตโนมัติแล้ว** ถ้าต้องการ cache ใช้ directive `"use cache"`
- Tailwind v4 ตั้งค่าใน CSS (`@theme`) ไม่มี `tailwind.config.js` แล้ว
- เอกสารฉบับตรงเวอร์ชันอยู่ใน `node_modules/next/dist/docs/` — อ่านจากตรงนั้นน่าเชื่อถือกว่าค้นเน็ต
